* Overview
Backport the MIPI DSI display pipeline from Linux v6.10 to U-Boot v2026.04 for Allwinner T113-S.

Pipeline: DE2 Mixer → TCON Top → TCON LCD0 → DSI Controller → D-PHY → ILI9881C Panel

* Phase 1: Clock and PHY Foundation [DONE]
- Verified T113-S CCU support for =CLK_BUS_MIPI_DSI= and =CLK_MIPI_DSI=.
- Ported sun6i MIPI D-PHY driver to U-Boot PHY framework.
- Implemented HS/CLK timing calculations and analog power-on sequences for A100/D1 variant.

* Phase 2: Display Pipeline Drivers [DONE]
- Ported sun6i MIPI DSI controller driver as U-Boot DSI host uclass.
- Added DSI TRI-mode support to TCON/LCDC with automatic frame output configuration.
- Extended DE2 driver for DSI output path and NCAT2-specific clock/reset handling.

* Phase 3: Panel and Device Tree [DONE]
- Ported ILI9881C panel driver with =hd50004c30= variant support.
- Integrated full display pipeline (Mixer0 → TCON Top → TCON LCD0 → DSI → Panel) into board DTS.
- Enabled =CONFIG_VIDEO=, =CONFIG_VIDEO_DE2=, and splash screen support in board defconfig.

* Phase 4: Solving potential display issue [DONE]
Deep-dive comparison against Allwinner brandy-2.0 BSP identified and fixed all discrepencies in the U-Boot display pipeline: corrected =CCSC01= offset (=0xFA050=),
disabled TCON CCIR CSC (=HV_IF_REG= bit 19), fixed ILI9881C command =0xCF=, cleared
DCSC/SMBL/VEP units, applied D-PHY =ANA1= bit-5 IC-version quirk, and zeroed stale
Combo PHY registers. Display verified correct on hardware for both ILI9881C and EK79007.

* Phase 5: Linux Kernel Display Issue [Progressing]
Symptom: start the device with linux, display gradient.bmp on LCD via MIPI DSI interface. 9 out of 10 times, it displays the image correctly, as showing in ./debug/captures/c.jpg. Sometimes, it displays the image incorrectly, as showing in ./debug/captures/e0.jpg.

Observations:
+ The symptom stays after soft reboot. When soft reboot via linux terminal, if the display was incorrect before reboot, it will display incorrectly after reboot as well. Vice versa;
+ The symptom won't stay after power cycle;
+ Enabling MIPI DSI splash in U-Boot makes the Linux display failure more frequent after handover;
+ U-Boot itself always displays correctly, even after a soft reboot;

Analysis:
+ D-PHY/DSI hardware state is not the root cause — U-Boot proves the link layer resets cleanly on soft reboot;
+ U-Boot uses a minimal subset of the display framework; Linux enables additional units (e.g., CSC, enhancement blocks) that U-Boot never touches;
+ After a soft reboot, these extra units may retain stale state from the previous Linux session, and Linux may not fully reinitialize them assuming clean power-on defaults;
+ Race conditions in Linux's multi-subsystem init sequence (PHY, DSI, TCON, DE2, panel) remain a possible cause, though less likely since the symptom persists across soft reboots;
+ Primary investigation should focus on what Linux enables that U-Boot does not, and whether Linux properly resets those units during probe;

Failure pattern:
+ Single failure mode: vertical banding / color channel separation (see =./debug/captures/incorrect0.jpg= and =incorrect1.jpg=);
+ The number of bands and colors vary between occurrences, suggesting a timing-dependent element (e.g., DSI lane skew or D-PHY PLL phase varying per boot);

Dmesg analysis (7 captures in =./debug/147048/=: 4 incorrect, 3 correct):
+ Linux display pipeline init sequence is identical across all correct and incorrect boots — same messages, same probe order, zero errors or warnings;
+ Regulator probe ordering varies due to async scheduling but does NOT correlate with display correctness;
+ Soft reboot vs power-cycle shows no kernel-side init difference;
+ Conclusion: the problem is entirely pre-kernel — the display outcome is determined by hardware state before Linux starts, not by how Linux initializes the pipeline;

** Known issue: DRM aggregate teardown memory corruption
When unbinding the =sun6i-mipi-dsi= platform driver, =component_del= triggers =sun4i_drv_unbind= which tears down the entire DRM device. =drm_fbdev_dma_setup= was called during bind, meaning the kernel fbcon (framebuffer console) is an active consumer. During =drm_dev_unregister=, the fbdev is removed, but fbcon may race with the teardown — it is a kernel-internal consumer unaffected by killing userspace processes. This was observed as a NULL =vm_mm= crash in an unrelated =sshd= process (NULL deref at offset 0x58 in =down_write= from =vma_prepare=, with unsymbolized return address on stack indicating slab/memory corruption). The crash is non-deterministic and may not reproduce on every unbind cycle. Low priority — only affects the unbind/rebind debug workflow, not normal operation.
