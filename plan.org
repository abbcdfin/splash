* Overview
Backport the MIPI DSI display pipeline from Linux v6.10 to U-Boot v2026.04 for Allwinner T113-S.

Pipeline: DE2 Mixer → TCON Top → TCON LCD0 → DSI Controller → D-PHY → ILI9881C Panel

* Phase 1: Clock and PHY Foundation [DONE]
- Verified T113-S CCU support for =CLK_BUS_MIPI_DSI= and =CLK_MIPI_DSI=.
- Ported sun6i MIPI D-PHY driver to U-Boot PHY framework.
- Implemented HS/CLK timing calculations and analog power-on sequences for A100/D1 variant.

* Phase 2: Display Pipeline Drivers [DONE]
- Ported sun6i MIPI DSI controller driver as U-Boot DSI host uclass.
- Added DSI TRI-mode support to TCON/LCDC with automatic frame output configuration.
- Extended DE2 driver for DSI output path and NCAT2-specific clock/reset handling.

* Phase 3: Panel and Device Tree [DONE]
- Ported ILI9881C panel driver with =hd50004c30= variant support.
- Integrated full display pipeline (Mixer0 → TCON Top → TCON LCD0 → DSI → Panel) into board DTS.
- Enabled =CONFIG_VIDEO=, =CONFIG_VIDEO_DE2=, and splash screen support in board defconfig.

* Phase 4: Solving potential display issue [DONE]
Deep-dive comparison against Allwinner brandy-2.0 BSP identified and fixed all discrepencies in the U-Boot display pipeline: corrected =CCSC01= offset (=0xFA050=),
disabled TCON CCIR CSC (=HV_IF_REG= bit 19), fixed ILI9881C command =0xCF=, cleared
DCSC/SMBL/VEP units, applied D-PHY =ANA1= bit-5 IC-version quirk, and zeroed stale
Combo PHY registers. Display verified correct on hardware for both ILI9881C and EK79007.

* Phase 5: Linux Kernel Display Issue [Progressing]
Symptom: start the device with linux, display gradient.bmp on LCD via MIPI DSI interface. 9 out of 10 times, it displays the image correctly, as showing in ./debug/captures/c.jpg. Sometimes, it displays the image incorrectly, as showing in ./debug/captures/e0.jpg. To be noted that the resolution of this screen is 720x1280, so actually the error pattern is horizental banding .

Observations:
+ The symptom stays after soft reboot. When soft reboot via linux terminal, if the display was incorrect before reboot, it will display incorrectly after reboot as well. Vice versa;
+ The symptom usually won't stay after power cycle;
+ Enabling MIPI DSI splash in U-Boot makes the Linux display failure more frequent after handover;
+ U-Boot itself always displays correctly, even after a soft reboot;
+ unbind and bind DSI device in linux won't fix the issue;
+ when black image got displayed incorrectly, the whole screen has a dark blue color. It is the same when application stop displaying image on screen;
+ when using modetest to show the test pattern, it seems correct. So, it doesn't looks like there is a const pattern added to the image, more like some sort of conversion are enabled;
+ unbind DSI device leaves the screen in normal blank state;
+ Both ./resources/solid_1f1f1f.bmp and ./resources/solid_5f5f5f.bmp are displayed when the system display in incorrect state. solid_1f1f1f.bmp displayed with a blue color 
 yet solic_5f5f5f.bmp displayed correctly. I strongly feel that the problem is in pixel conversion, in which case, some pixel with specific data (or like in a range) got 
 converted to different color and show incorrectly. 

Failure pattern:
+ Single failure mode: horizontal banding (see =./debug/captures/incorrect0.jpg= and =incorrect1.jpg=);
+ The number of bands and colors vary between occurrences, suggesting a timing-dependent element (e.g., DSI lane skew or D-PHY PLL phase varying per boot);

** Findings (2026-04-04)

*** Blue channel 6-bit quantization
The user identified that the incorrect display shows the blue channel interpreted as 6 bits
instead of 8 bits, while red and green are correct. Verified with gradient_blue.bmp:
- Correct: smooth gradient (see =./debug/captures/blue.gradient.correct.jpg=)
- Incorrect: visible stair-step banding (see =./debug/captures/blue.gradient.incorrect.jpg=)

*** Register dumps are identical between correct and incorrect boots
Comprehensive register dumps covering the full pipeline (CCU, DE2 Global/Blender/UI1/VI0,
TCON TOP/LCD0 full 0x200 range, DSI 0x200 range, D-PHY 0x120 range, VEP/FCC/DCSC/CCSC01)
show NO differences between correct and incorrect Linux boots.

Tools created:
- U-Boot: =dispdump= command (=u-boot/cmd/sunxi_disp_dump.c=)
- Linux: =utils/dump_display_regs.sh= (shell script using devmem2)
- Kernel: commit =51d35125e= (in-kernel PRE-INIT dump in =sun6i_mipi_dsi.c=)

Dumps collected in =./debug/147048.extensive.dump/=.

*** Reset cycle patch (did not fix)
Added =reset_control_assert()= before =reset_control_deassert()= for DE2 mixer
(=sun8i_mixer.c=) and TCON_TOP (=sun8i_tcon_top.c=). This did NOT fix the issue,
ruling out residual internal FIFO/state-machine state from U-Boot as the cause.

*** U-Boot vs Linux TCON register differences
Comparing U-Boot post-display and Linux post-display dumps reveals significant TCON
configuration differences:

| Register (TCON offset) | U-Boot         | Linux          | Notes                              |
|------------------------+----------------+----------------+------------------------------------|
| FRM seeds (0x014-0x038)| all 0x0        | 0x11111111 + tables | Linux writes seeds; FRM disabled in both |
| TCON0_CTL (0x040)      | 0x810001e0     | 0x81000000     | U-Boot: start_delay=0xF, IF mode bits |
| TCON0_DCLK (0x044)     | 0xf0000004     | 0x80000004     | U-Boot: bits 29:28 extra           |
| TCON0_BASIC1 (0x04c)   | 0x03470031     | 0x00000000     | U-Boot programs htotal/hbp         |
| TCON0_BASIC2 (0x050)   | 0x0a500013     | 0x00000000     | U-Boot programs vtotal/vbp         |

*** Key open question
All these are expected differences (U-Boot and Linux configure differently). But since
correct and incorrect Linux boots have identical registers, neither U-Boot nor Linux
register configuration is the direct cause. The root cause must be in:
1. Panel internal state (ILI9881C DSI receiver byte alignment)
2. DSI link synchronization race during init
3. Internal FIFO/pipeline state not visible in any register

** Known issue: DRM aggregate teardown memory corruption
When unbinding the =sun6i-mipi-dsi= platform driver, =component_del= triggers =sun4i_drv_unbind= which tears down the entire DRM device. =drm_fbdev_dma_setup= was called during bind, meaning the kernel fbcon (framebuffer console) is an active consumer. During =drm_dev_unregister=, the fbdev is removed, but fbcon may race with the teardown — it is a kernel-internal consumer unaffected by killing userspace processes. This was observed as a NULL =vm_mm= crash in an unrelated =sshd= process (NULL deref at offset 0x58 in =down_write= from =vma_prepare=, with unsymbolized return address on stack indicating slab/memory corruption). The crash is non-deterministic and may not reproduce on every unbind cycle. Low priority — only affects the unbind/rebind debug workflow, not normal operation.
